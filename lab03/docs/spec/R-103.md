# R-103 越权用例集（REQ-026）

## 两层，缺一不可

| 层 | 文件 | 断言什么 | 证明什么 |
|---|---|---|---|
| 判定层 | `tests/test_m1.py::test_deny_matrix` | `can()` 返回 `False`，共 30 条（横向 15 + 纵向 15） | 权限矩阵本身没漏格、没多格 |
| 入口层 | `tests/test_m1_entries.py` | 打真实 HTTP 视图，49 条（34 条拒绝 + 15 条正常链路与边界） | 视图真的调了权限检查；业务函数没执行；响应不含商品内容；每次拒绝写了一条 denied 日志 |

只做判定层是不够的：`can()` 判得对，但视图或用例层忘了调它，接口照样能被越权访问。
Day 2 就出过这种真实反例——`save_draft()` 漏了 `product.create`，管理员能建商品，
而 Day 1 的矩阵用例全绿。

## 入口层每条用例断言四件事

1. 响应 403（不是 200，也不是 500）
2. 响应体里没有目标商品的标题（不借错误信息泄露数据）
3. `OperationLog` 总数 +1，且最新一条 `result=denied`
4. 商品 `status` 与 `version` 没变、标题没变（业务确实没执行）

覆盖的动作：`submit` / `update` / `images` / `revise` / `audit` / `unpublish` / `withdraw` /
`takedown` / `terminate` / `delete`，外加 `POST /api/products/` 新建草稿。
拒绝身份覆盖游客（匿名）、客服、管理员、他人会员，以及管理员自审自己的商品。

## 日志四要素

拒绝留痕要带：操作者 ID、目标 ID、IP、端类型。
`tests/test_m1.py::test_denied_action_writes_log` 断言这四项都在；
入口层用 `_deny()` 统一写日志，所以 34 条拒绝用例同时验证了"统一记日志"这件事。

## 日志只追加（REQ-022 的底）

`operation_log` 表上有两个数据库触发器，`UPDATE` 与 `DELETE` 都会被拒绝
（`operation_log is append-only`）；PostgreSQL 下抛的是 `ProgrammingError`，断言用父类
`DatabaseError` 并匹配 `append-only`。
