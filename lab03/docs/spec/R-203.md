# R-203 内容修改与版本号校验（REQ-007、REQ-004/005 的改稿）

## 两种改稿入口

| 入口 | 用于 | 函数 | 结果状态 |
|---|---|---|---|
| 草稿/驳回稿改内容 | 还没公开的稿子 | `update_draft(product, *, actor, expected_version=None, **fields)` | 草稿（已驳回的稿子改完自动回草稿） |
| 已发布/已预售改内容 | 线上商品 | `revise_content(product, *, actor, expected_version, **fields)` | 待审核，版本号 +1 |

## 行为实例

| # | 场景 | 预期 |
|---|---|---|
| 1 | 卖家在已发布商品上改价 | 变待审核，版本号 +1，开出待审流水 |
| 2 | 审核通过后再看 | 回到已发布，版本号保持 |
| 3 | 两个编辑页都拿着 v1，先提交者成功 | 版本变 v2 |
| 4 | 后提交者仍提交 v1 | **409**「商品已被修改，请刷新后重试」，库里内容仍是先提交者的 |
| 5 | 交易中的商品改内容 | 拒绝（状态图二：交易中不得改内容） |
| 6 | 没有可改字段 | 拒绝 |
| 7 | 把价格改成 -1.00 再提交 | 拒绝，状态与价格都不变（写库前校验） |
| 8 | 改了标题但忘了传图 | 拒绝，不进入待审核 |
| 9 | 已驳回的稿子改稿 | 自动回草稿，可再次提交 |
| 10 | 用旧版本号改草稿 | 拒绝（草稿也带版本号） |

## 契约

- `update_draft(product, *, actor, expected_version=None, **fields) -> Product`
- `revise_content(product, *, actor, expected_version, **fields) -> Product`
- 内容字段白名单 `CONTENT_FIELDS = ("title", "description", "price", "category", "brand", "is_presale")`
- **ABA 防线放在数据库上**：`revise_content` 不是"先存内容再转状态"，而是一条
  `UPDATE product SET status=待审核, version=version+1, ...内容 WHERE id=? AND version=? AND status IN (已发布,已预售)`，
  `rowcount != 1` 就抛 `VersionConflict`。内存里的版本号只能当提示，不能当判据——
  两个请求各自把对象读进内存时，双方看到的版本号都可能"对得上"
- 版本号用 `F("version") + 1` 自增，避免读改写丢更新
- 版本冲突 → HTTP 409；内容不合法 → 400；不是本人 → 403（`catalog/views.py::json_errors`）
