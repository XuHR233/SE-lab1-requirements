## 原方案与本次差异

| 事项 | 原设计 / 变更前 | CR-001 |
|---|---|---|
| 会话 | 买卖双方发言；有关联工单时工作人员可以只读查看 | 接单人进入同一串会话发文字及图片，双方可见；标记客服/管理员身份。其他工作人员仍按原纠纷职责只读；无关第三方仍拒绝。 |
| 处置位置 | 处置入口单独放在工单卡 | Lab2 沟通页右栏在商品图下放「裁定纠纷」「驳回介入」。前者保留退款/终止两种结论，后者恢复履约；须写明处理说明。买卖双方不显示这些入口。 |
| 唯一处置权 | 接单记录首位处理人，但裁定和驳回未核查当前处理人 | 每单一工单、一个处理位。未接单不可发言或处置；已接单只有该账号可操作；其他客服和管理员都不能越过接单或抢当前处理位。 |
| 升级 | Lab3 计划有「升级」一态，原验收实现无升级流程 | 当前客服填原因转交并交回处理权。等待时无人可裁定；仅一位管理员可以接管，接管后才可发言、裁定或驳回。管理员也可直接接未分派、未升级的工单。 |
| 结案 | 退款／终止／驳回沿用 R-502 及 M4 联动 | 订单、商品、退款规则不变；订单与工单原子结案，保留唯一裁定人。接单、转交、接管及裁定/驳回可按订单号在后台日志查询。 |

## 实现说明与验证

- 工单持久化状态仍为 `待处理/已处理`，由处理人和升级时间派生 `待接单/处理中/待管理员接管/管理员处理中`，由结论区分退款、终止和驳回。不是原计划的七个独立状态，也未增加「已和解」单独落点。
- 同一工单接单、转交、发言复核和结案在 PostgreSQL 用行锁串行；沿用交易原用例，不直接改订单资金表。迁移为旧待处理工单补关联会话，不重置既有处理人。交回/结案后工作人员的历史消息仍可读，不能继续作为处理人发言。
- 页面仍复用 Lab2 原样式；多角色浏览器之间用「刷新」拉取最新消息和处理进度，本次没有引入推送。短信、支付、退款仍是回环内测，不接外部渠道。
